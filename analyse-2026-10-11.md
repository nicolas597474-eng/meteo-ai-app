## 3. Vos trois captures d'écran : état réel et point d'insertion

Les trois cartes appartiennent au **même sous-système** (qualification des capteurs citoyens) et butent sur **le même chaînon manquant**.

### Le socle serveur est déjà complet

`server/openSenseMapQualificationService.ts` est un module **pur et déterministe** (aucun accès base ni réseau), versionné `citizen-qualification-v2`, appliqué aux sources `opensensemap` et `cwop`. Il expose déjà tout le nécessaire :

```ts
// line 41-52 — les portes de qualification
minimumComparisons: 7      // comparaisons alignées
minimumDistinctDays: 3     // jours distincts (les jours portent l'échantillon)
minimumOfficialReferencesPerComparison: 2
maximumOutlierShare: 0.3
acceptanceMinC: 1 → acceptanceMaxC: 3
```

```ts
// line 80-93 — la preuve, déjà calculée
export type OpenSenseMapQualificationEvidence = {
  comparisons: number;          retainedComparisons: number;
  outlierComparisons: number;   distinctDays: number;
  officialStationsUsed: string[];
  meanOfficialDisagreementC: number | null;  acceptanceBoundC: number | null;
  meanAbsoluteErrorC: number | null;         meanBiasC: number | null;
  firstComparedAt: string | null;            lastComparedAt: string | null;
};
```

Les motifs d'échec contiennent même **déjà le libellé exact** demandé par la carte 3 :

```
line 292 : `Historique insuffisant : ${comparisons.length}/${7} comparaison(s) alignée(s)…`
line 301 : `… ${comparisons.length} comparaison(s) mais seulement ${distinctDays}/${3} jour(s) distinct(s) ;`
```

Le verdict est persisté et relu via `getWeatherStationQualificationVerdicts` (`server/db.ts:1165`).

### Le chaînon manquant

> **La preuve de qualification ne franchit jamais la frontière client.** Le type `StationQualificationEntry` (`client/src/components/weather/StationQualificationSection.tsx:21-41`) et la charge utile de `searchStations` (`server/routers/weather.ts:1525`) transportent `qualificationStatus` et `exclusionReason`, **jamais `evidence`**.

Un `grep` sur `evidence` dans `StationQualificationSection.tsx` et `CitizenFusionImpactSection.tsx` ne renvoie **rien**. Les trois chantiers se réduisent donc, côté serveur, à **exposer une donnée déjà calculée**.

**Statut : non implémenté.** Mais **aucune modification serveur n'est nécessaire.**

### Carte 2 — « Indicateur visuel de progression de la qualification »

**Statut : non implémenté** (l'état actuel est binaire, pas progressif).

Ce qui existe : `StationQualificationSection.tsx`, rendue dans le Laboratoire (`ReliabilityLaboratory.tsx:369`), affiche par station un **badge** — `Station officielle` / `Capteur citoyen en validation` / `Capteur citoyen validé` / `Exclu` — via `getStationQualificationBadge` (`client/src/lib/stationCandidateStatus.ts`), plus la source, l'âge du relevé, la distance, les variables présentes et le motif d'exclusion.

Ce qui manque : **aucune notion d'avancement**. Un capteur à 1/7 comparaisons et un capteur à 6/7 sont visuellement identiques. Or les deux quantités qui progressent sont précisément celles que le serveur calcule déjà :

```
comparaisons restantes = max(0, 7 − evidence.comparisons)
jours restants         = max(0, 3 − evidence.distinctDays)
```

**Implémentation recommandée**
1. Étendre la charge utile de `searchStations` (ou ajouter un endpoint dédié) avec un `qualificationEvidence` **uniquement pour les capteurs citoyens** — même périmètre que le verdict persisté.
2. Calculer la preuve à la demande : `getStationObservationsForQualification(stationIds, sinceMs)` (`server/db.ts:1150`) alimente déjà le service pur.
3. Afficher une barre sobre indexée sur la **porte la plus contraignante des deux** (« 4/7 comparaisons · 2/3 jours »), et non sur un pourcentage composite inventé.
4. Cas particulier à traiter : `excluded` — afficher la raison, pas une barre de progression (le capteur ne progresse plus).

### Carte 3 — « Nombre exact de comparaisons restantes avant validation, dans la section Laboratoire »

**Statut : non implémenté, et c'est le même blocage que la carte 2.**

`ReliabilityLaboratory.tsx` (387 lignes) compose déjà : `ReliabilityTrendChart`, `YesterdayVerificationPanel`, `ReliabilityNotesSummary` / `HorizonEvidenceSection` / `VariableEvidenceSection`, `LargestErrorsSection` / `MethodologySection` / `ModelComparisonSection`, puis `StationQualificationSection` (ligne 369) et `CitizenFusionImpactSection` (ligne 377).

Une recherche de `comparaisons restantes` / `remainingComparisons` sur tout `server/`, `client/`, `shared/` ne renvoie **qu'un commentaire** dans le service (`openSenseMapQualificationService.ts:11`). Rien dans le Laboratoire.

**Point de rigueur — corrigé après vérification.** J'avais d'abord écrit qu'afficher le restant depuis `retainedComparisons` produirait un « 0 restant » sur un capteur toujours non validé, car la porte teste `comparisons.length` (ligne 288) alors que `retainedComparisons` est calculé **après** l'élagage robuste.

**Cette affirmation était trop forte, et un test écrit depuis l'a réfutée.** L'élagage ne s'exécute qu'*après* les deux portes de suffisance : tout profil encore `candidate` est donc retourné par un retour anticipé, où `retainedComparisons === comparisons`. Les deux grandeurs coïncident pour **tous** les profils candidats — l'invariant est désormais vérifié par test (`documente que retainedComparisons égale comparisons pour tout candidat`).

Le restant est malgré tout dérivé de `evidence.comparisons`, la grandeur que la porte teste réellement : c'est un choix **défensif**, qui reste juste si la structure de retours anticipés de l'évaluateur évolue. Ce n'est pas un bug corrigé.

**Implémentation recommandée** : une ligne dédiée dans `StationQualificationSection` (« Encore N comparaison(s) et M jour(s) distinct(s) — sur 7 et 3 »), alimentée par la preuve du point 3.2. C'est **le même correctif que la carte 2** : une seule exposition serveur débloque les deux cartes.

*(Écart expliqué : 251 fichiers `.test.ts`/`.test.tsx` sur disque − 2 fichiers `shared/` = **249** fichiers exécutés.)*

### F2 — Les trois cartes sont un seul chantier 🔵

Les cartes 2 et 3 se résolvent par **une exposition serveur unique** (`qualificationEvidence` sur les capteurs citoyens) ; la carte 1 ne demande **aucun changement serveur** (les statuts sont déjà sur le fil). Traiter les cartes 2+3 ensemble évite de plomber la charge utile deux fois et de dupliquer la logique de seuils.

*Point d'attention* : les seuils `7` et `3` ne doivent **pas** être recopiés côté client. Ils vivent dans `OPEN_SENSE_MAP_QUALIFICATION_GATES` (`openSenseMapQualificationService.ts:41`) — le client doit recevoir la progression **et** les bornes, ou mieux, un `remaining` calculé serveur.

### F3 — Risque de duplication de la logique de statut 🟡

`Ranking.tsx:273-276` filtre sur `qualificationStatus` directement, tandis que `StationQualificationSection.tsx` passe par `getStationQualificationBadge`. Deux chemins pour une même vérité, dont **un seul est testé** (`client/src/lib/stationCandidateStatus.test.ts`). Le filtre de la carte 1 est l'occasion de converger sur le helper testé — cohérent avec le commit de tête, « *align citizen station qualification contracts* ».

### F4 — Fichiers très volumineux 🟡

`server/db.ts` (2 720), `server/routers/weather.ts` (2 036), `server/scheduledHandlers.ts` (1 850), `Dashboard.tsx` (1 571). Ce sont les points de friction pour toute intervention dans le sous-système de qualification, puisque les trois cartes y touchent. Une découpe incrémentale par domaine (ex. `db/qualification.ts`) resterait sans impact fonctionnel.

### F5 — Environnement non installé ⚪

`node_modules` est absent du dépôt (correct). L'installation se fait sans friction : `npx pnpm@10.4.1 install --frozen-lockfile`, puis `tsc` et `vitest` passent tels quels — aucune variable d'environnement requise pour la suite de tests (le `vitest.setup.ts` et `testNetworkGuard.ts` isolent du réseau).

Trois décisions de conception méritent d'être explicitées :

1. **La preuve réutilise l'évaluateur** au lieu de le réimplémenter. `deriveOpenSenseMapVerdicts` retournait déjà les `profiles` complets avec leur `evidence` : les réutiliser garantit que l'écran affiche exactement ce que le job calcule.
2. **Endpoint dédié plutôt qu'extension de `searchStations`** : la preuve parcourt 30 jours d'historique pour les capteurs *et* les témoins officiels — trop lourd pour le chemin de recherche courant (Classement, Tableau de bord).
3. **Lecture seule, par conception** : consulter sa progression ne peut pas promouvoir un capteur ; le verdict reste posé par le chemin planifié.

Cas limites traités : un capteur **validé** affiche « Qualification acquise » et aucun restant ; un capteur **exclu** affiche « Capteur écarté » et **aucun restant** — l'écran ne laisse jamais croire qu'une validation approche pour un capteur écarté ; sans preuve disponible, **aucune barre n'est affichée** (aucun avancement inventé).

### R3 — filtre carte des capteurs citoyens ✅

`client/src/components/StationMap.tsx` : bascule « Masquer les capteurs citoyens non qualifiés (N) », **désactivée par défaut** — la carte ne masque jamais une station sans demande explicite. L'effectif masqué est annoncé sur le bouton (« Afficher toutes les sources (M masquée(s)) »), conformément à l'invariant du dépôt : rien ne disparaît en silence. Le badge de qualification réel apparaît aussi dans l'infobulle, et la légende précise que **la couleur encode la fraîcheur, jamais la qualification**.

**Sémantique retenue, et pourquoi elle a changé.** Une première version lisait la carte au pied de la lettre : n'afficher *que* les capteurs citoyens qualifiés, stations officielles comprises. Vérification faite, cette lecture a un défaut rédhibitoire : **la qualification se définit par l'accord avec les stations officielles SYNOP**. Les masquer retire de la carte l'étalon qui donne son sens au mot « qualifié » — on ne peut plus juger si un capteur validé est proche d'un témoin officiel. Et sans capteur qualifié, la carte devient vide, état indiscernable d'une carte en panne.

Le filtre retire donc les capteurs citoyens **en validation et exclus**, et conserve tout le reste. Le libellé annonce ce qu'il retire au lieu de promettre « uniquement » : le texte et le comportement disent la même chose.

Restreindre volontairement au périmètre citoyen est aussi un choix : une source écartée pour une autre raison (station Netatmo inactive, par exemple) n'est pas concernée — le filtre répond à une question sur la qualification citoyenne, pas sur l'activité en général.

### R4 — convergence des contrats ✅

- `getStationDisplayStatus` est désormais la **seule** définition du statut affiché : `Ranking.tsx` s'appuie dessus (`candidateSources`, `ignoredSources`) au lieu de refiltrer à la main.
- **Correction d'une affirmation du présent rapport.** Il était écrit ici « équivalence sémantique vérifiée cas par cas avant bascule ». **C'était faux**, et un contrôle exhaustif des 120 combinaisons (source × statut × activité × type) l'a établi : **9 divergences** subsistaient. Le helper implémente l'intention réellement visée, pas le comportement littéral précédent.

  La divergence porte sur une station **non citoyenne inactive** (Météo-France, Netatmo) dont le statut vaut `"validated"` — c'est-à-dire **tous** les cas, puisque `"validated"` est le défaut du schéma (`drizzle/schema.ts:320`). L'ancien filtre portait un garde `!== "validated"` trop large : ces stations n'étaient comptées **ni** dans « Candidates » **ni** dans « Écartées ». Elles disparaissaient de tous les compteurs.

  **Conséquence visible en production : le compteur « Écartées » du Classement peut augmenter.** Le changement est conservé parce qu'il supprime une disparition silencieuse — l'anti-patron que ce dépôt s'interdit — et parce que le routeur modélise déjà ces stations (`excludedPhysicalStations`, `exclusionReasons`). Il est documenté dans `Ranking.tsx` et figé par trois tests. Si l'identité stricte des compteurs est préférée, la variante est explicite : filtrer sur `"excluded"` **et** `qualificationStatus !== "validated"`.
- Nouveaux prédicats partagés `isCitizenQualificationSource` / `isQualifiedCitizenStation` dans `client/src/lib/stationCandidateStatus.ts`, utilisés par la carte.
- `Ranking.test.ts` : l'assertion qui vérifiait le littéral `station.qualificationStatus !== "validated"` est remplacée par une assertion sur le nouveau contrat (le comportement « un validé n'est jamais écarté » reste couvert, par le helper et son test dédié).
